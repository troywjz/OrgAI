# 写作规范

本规范适用于 Blueprint 的全部文档和 PPT。核心读者是企业和组织的管理决策者：他们不需要知道技术怎么实现，需要知道它值不值得投入、为什么选它。

## 1. 技术讲解规则

讲任何一项技术，按以下顺序和篇幅组织：

| 部分 | 要求 | 篇幅 |
|---|---|---|
| 一句话本质 | 用一句话讲清概念、原理和本质，不出现公式和未解释的术语 | 1 句 |
| 现实价值 | 它在现实世界、尤其在企业和组织里解决什么问题，带来什么可衡量的结果 | 主体 |
| 差异化价值 | 和相近技术比，什么情况下选它、什么情况下不选它 | 主体 |
| 成本与门槛 | 需要什么数据、算力、人才、周期，大致量级 | 简要 |
| 成熟度与风险 | 技术成熟度、主要风险、常见误区 | 简要 |

"一句话本质"的写法示例：

> RAG（检索增强生成）：先从组织自己的资料库里查到相关内容，再让大模型基于这些内容回答，本质是给大模型配一个随时可查的"内部档案室"。

不合格的写法：只给定义（"RAG 是一种结合检索与生成的架构"），或者展开讲向量数据库、嵌入模型等实现细节。

## 2. 差异化对比规则

决策者最常问的是"为什么用这个而不是那个"。每项技术至少与一项相近或可替代的技术对比，用统一的对比维度：

| 维度 | 说明 |
|---|---|
| 解决的问题 | 两者各自最适合的问题类型 |
| 效果上限 | 能做到多好 |
| 投入成本 | 数据、算力、人力、时间 |
| 上线速度 | 从启动到可用的周期 |
| 可控性 | 结果是否可解释、可审计、可修正 |
| 数据要求 | 需要多少、什么质量的数据，数据是否出域 |
| 维护负担 | 上线后的持续投入 |

对比结论写成选择规则，例如："知识经常更新、需要标注出处，选 RAG；需要模型掌握固定的行业表达方式和推理习惯，选微调；两者常组合使用。"

典型对比组（在 [01 技术全景](docs/01-tech-landscape/README.md) 中落实）：提示工程 vs RAG vs 微调；通用大模型 vs 领域模型 vs 小模型；公有云 API vs 私有化部署 vs 混合部署；RPA vs AI 智能体；传统机器学习 vs 大模型；自研 vs 采购 vs 开源二次开发。

## 3. 面向组织类型的区分

内容默认以企业为主。以下差异明显时，单独标注适用对象：

| 组织类型 | 需要单独说明的方面 |
|---|---|
| 企业 | 收入增长、成本下降、竞争优势 |
| 政府机关 | 服务效能、群众满意度、政务数据合规、信创与国产化要求、财政预算与采购流程 |
| 事业单位 | 公益属性、编制与考核、资金来源 |
| 非营利组织 | 资金有限、志愿者参与、捐赠方的透明度要求 |

标注方式：在段落前加 `【政府】`、`【事业单位】`、`【非营利】` 前缀，或在章节末尾设"不同组织类型的差异"小节。

## 4. 语言风格

用决策者的语言，不用工程师的语言。说"把客服首次响应时间从 4 小时降到 5 分钟"，不说"实现了低延迟的智能问答"。

具体要求：每段一个观点；先结论后理由；用数字代替形容词，没有可靠数字时写明是估计并给出范围；不用"赋能""抓手""颠覆""革命性"等空泛词；专业术语第一次出现时给出中文全称和英文缩写，并收录到 [GLOSSARY.md](GLOSSARY.md)。

## 5. 数据与来源

所有数字、案例、市场判断必须有来源，登记到 [references/sources.md](references/sources.md)，正文用 `[S编号]` 标注。行业报告注明发布机构和年份。超过两年的数据需注明时效。不使用无法核实的数字。

本项目公开开源，不得写入任何涉密信息、未公开的客户数据或个人信息。案例中的组织如未公开披露，一律匿名化处理。

## 6. 文档与 PPT 的关系

Markdown 正文是唯一事实来源。PPT 和 Word 从正文提炼，不在 PPT 中出现正文没有的结论。每个章节 README 末尾设"PPT 要点"小节，列出该章进入 PPT 的 3 到 5 个核心信息。

## 7. 文件命名

目录和文件使用小写英文加连字符，前缀两位编号控制顺序，例如 `01-tech-landscape/03-rag.md`。文档标题和正文使用中文。
