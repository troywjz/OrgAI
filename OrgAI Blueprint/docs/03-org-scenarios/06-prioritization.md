# 场景优先级：先确认边界，再比较价值与可行性

> 状态：方法初稿。评分用于组织讨论，不是法律合规结论或项目效果证明；权重和阈值应由组织结合目标、预算和风险承受能力确定。

风险贯穿设计、部署与运营的思路可参考 NIST AI 风险管理框架 [S010]；本文的门槛、评分和权重为项目自拟工具，并非该框架规定的评分标准。

## 1. 先把候选场景写清楚

每个候选场景应至少明确：服务对象、当前工作流程、业务负责人、现行方案及痛点、期望结果、所需数据和系统、影响对象与出错后果。使用 [场景卡](../../templates/scenario-card.md) 记录，数据或基线未知时写“待确认”，不虚构数字。

## 2. 先审查风险门槛

业务、技术和风险相关人员先共同确认以下问题，并记录依据和负责人：

1. **用途和责任：** 有无明确的业务用途、负责角色、人工复核和必要的申诉或纠错渠道？特别是影响个人权益的决定，谁负责最终判断？
2. **数据与权限：** 数据是否可用于这一目的，是否有适用的授权、访问控制和处理边界？部署、供应商、接口和日志会接触什么信息？
3. **可控性：** 出错、越权或系统不可用会造成什么后果？能否测试、限制权限、发现问题、暂停并回退？
4. **适用要求：** 根据所在地、组织、行业、用途和数据核查相关制度、法律、采购或安全要求，而非默认所有组织要求相同。

结果只用三种状态：**通过**（已确认必要条件及控制措施）、**待补充**（资料或控制措施不足）、**不通过**（当前条件下必要要求不能满足或风险无法接受）。只有通过门槛的场景才进入真实业务试点排序；待补充的应先解决问题，不通过的应停止或重新设计。涉及必要要求时，业务收益和加权分都不能抵消未满足的门槛。脱离真实业务与真实敏感数据的演示可另行用于澄清可行性，但不视作业务试点或上线批准。

## 3. 对通过门槛的场景评分

下面是一套可调整的示例尺度。价值和可行性各评 1—5 分，分数越高越有利；评分必须有理由和证据，不同意见及不确定性应保留。

| 分数 | 价值：对组织目标的预期贡献 | 可行性：在现有条件下完成并持续运营的可能性 |
|---|---|---|
| 1 | 目标不清或受益很小 | 关键数据、系统或责任人均缺乏 |
| 2 | 有潜在用途，但受益对象和衡量方法不清 | 存在重大缺口，短期内难以处理 |
| 3 | 目标、受益对象和指标基本明确，价值仍待验证 | 大部分条件具备，仍有可识别的缺口和解决计划 |
| 4 | 目标重要、受影响范围和基线较清楚，有合理的价值依据 | 数据、系统、人员和预算基本可用，主要缺口有负责人 |
| 5 | 与重点目标高度相关，收益和影响范围有较强依据且可衡量 | 条件已验证，集成、复核和维护责任清楚，剩余不确定性较小 |

价值可综合考虑服务质量、时间、成本、收入、风险和公平性等，不应把公共组织的价值强行折算为收入。可行性需考虑数据可用及质量、系统集成、人员技能、预算、采购和后续维护；以最薄弱条件约束判断，不能只看模型演示。

**排序示例：** 若组织决定更重视价值，可采用 `优先分 = 0.6 × 价值分 + 0.4 × 可行性分`。这是演示权重，不是经过验证的行业标准；也可由组织事先调整权重。只有门槛通过的项目才计算，分数仅作为讨论顺序。遇到分数接近、证据不足或资源互斥时，比较假设、影响群体和投入，再由负责人决定；不要制造小数精度代表客观确定性。

## 4. 从排序到行动

对优先候选项写明：方案与非 AI 基线、样本来源及权限、评价指标与现状、预算上限、人员分工、人工复核、期限、停止和回退条件。风险高或后果严重的任务，即使价值高，也可能需要缩小范围或改变人机分工。试验结束后根据质量、实际总成本、服务对象反馈与风险记录，决定继续、修改或停止。

**示意，非真实案例：** 一个机构考虑用内部制度问答减少查找时间。先确认制度版本管理、人员访问权限和错误回答的复核责任；条件尚不清楚时标记“待补充”。条件确认后，比较关键词搜索和带出处的问答，用相同问题集记录找对资料的比例、完成时间及人工复核工作量，再由该机构确定是否值得试点。

## 5. PPT 要点

- 先明确业务目标和风险门槛，再比较价值与可行性。
- 通过门槛不是效果证明；试点须事先写好基线、复核、预算和停止条件。
- 分数与权重是讨论工具，不能替代证据、责任人判断或适用要求。
